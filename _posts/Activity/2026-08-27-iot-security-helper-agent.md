# 1. 프로젝트 배경

상명 AI 서비스에서 RAG, Text2SQL, LangGraph를 실습하면서 팀 프로젝트를 진행했다.

처음에는 문서 기반 검색이랑 DB 조회를 따로 구현하는 느낌이 강했다. PDF를 넣고, 질문을 던지고, 관련 문서를 찾아 답하는 구조. 그 다음에는 CSV나 테이블 데이터를 DB에 넣고 자연어 질문을 SQL로 바꿔 조회하는 구조.

기능만 보면 각각 따로도 의미가 있다. 그런데 서비스 형태로 묶으려니까 따로 두면 애매했다.

사용자는 “이 질문은 RAG로 물어봐야겠다”, “이건 DB 조회가 맞겠다” 이렇게 생각하지 않는다. 그냥 묻는다.

예를 들면 이런 식이다.

```text
웹캠이 혼자 움직이는데 해킹인가요?
공유기에 모르는 기기가 연결됐어요.
스마트 도어락 비밀번호는 어떻게 관리해야 하나요?
스마트 기기 해킹은 어디에 신고하나요?
```

이런 질문을 받았을 때 에이전트가 알아서 검색 방식까지 고르게 만들고 싶었다. 그래서 주제를 **IoT 디바이스 보안 점검 도우미**로 잡았다.

# 2. IoT 보안을 선택한 이유

IoT는 보안이랑 하드웨어가 같이 보이는 주제라서 선택했다.

웹 보안은 요청과 응답, 인증과 세션이 중심이다. 반면 IoT는 기기 자체가 있다. 웹캠, 홈캠, 공유기, 스마트 도어락, 스마트TV처럼 집 안에 놓이는 물건이다.

그래서 “해킹됐나요?”라는 질문도 조금 다르게 봐야 했다.

단순히 취약점 이름을 알려주는 게 아니라,

- 전원을 꺼야 하는지
- 공유기 비밀번호를 바꿔야 하는지
- 앱에서 연결된 기기 목록을 봐야 하는지
- 펌웨어 업데이트를 해야 하는지
- 어디에 신고해야 하는지

이런 답이 필요하다.

처음에는 하드웨어 보안 쪽을 너무 깊게 잡으려고 했다. ESP32, STM32, JTAG, UART, secure boot, flash encryption 같은 키워드를 중심으로 잡으면 기술적으로는 멋있어 보인다.

그런데 발표와 데모를 생각하면 너무 개발자용이었다. 그래서 방향을 조금 틀었다. 내부적으로는 IoT 하드웨어·보안 문서를 쓰되, 화면과 답변은 일반 사용자가 이해할 수 있게 만들었다.

# 3. 사용한 데이터

데이터는 크게 두 종류로 나눴다.

하나는 PDF 문서다. KISA IoT 보안 가이드, 홈·가전 IoT 보안 가이드, STM32 디버깅 가이드, ESP32-H2 기술 문서를 RAG 검색 대상으로 사용했다.

다른 하나는 구조화된 DB다. 신고 기관, 사고 유형, IoT 보안 항목, MCU 보안 기능처럼 정확한 목록이나 연락처가 필요한 정보는 Supabase 테이블로 분리했다.

대략 이런 역할이다.

| 구분 | 맡긴 일 |
|------|---------|
| Qdrant RAG | PDF 문서에서 보안 원리, 점검 방법, 하드웨어 설명 검색 |
| Supabase Text2SQL | 신고 기관, 사고 유형, 보안 항목 목록 조회 |
| LangGraph | 질문 의도에 따라 RAG / DB / 통합 경로 선택 |
| Streamlit | 일반 사용자가 볼 수 있는 대화형 화면 구성 |

처음에는 PDF 검색만 있어도 될 것 같았다. 그런데 “해킹 의심되면 어디에 신고해?” 같은 질문은 문서 검색보다 DB 조회가 낫다. 전화번호나 기관명은 문장으로 생성하면 안 되고, 정확한 값을 꺼내와야 한다.

반대로 “웹캠이 혼자 움직일 때 뭘 해야 해?”는 단순 DB 조회만으로 부족하다. 대처 순서와 이유를 설명해야 한다.

그래서 두 경로를 같이 쓰는 구조가 필요했다.

# 4. LangGraph 구조

전체 흐름은 LangGraph로 구성했다.

![IoT 보안 점검 도우미 LangGraph 워크플로우](/image/2026-08-27-iot-security-helper/langgraph-workflow.png)

핵심은 질문을 바로 답변 생성으로 보내지 않는 것이다. 먼저 질문을 정리하고, 의도를 분류한 뒤에 경로를 나눈다.

```text
질문 분석
→ 의도 분류
→ RAG 검색 / DB 조회 / RAG+DB 통합
→ 답변 생성
→ 답변 검증
```

의도는 네 가지로 나눴다.

| 의도 | 처리 방식 |
|------|-----------|
| general | 서비스 소개나 일반 대화 |
| iot_consult | PDF 기반 보안 가이드 검색 |
| database | 신고 기관, 사고 유형, 보안 항목 DB 조회 |
| hybrid | 문서 검색과 DB 조회를 함께 실행 |

예를 들어 “웹캠이 해킹된 것 같은데 어떻게 점검하고 어디에 신고해?”는 `hybrid`로 보내야 한다.

이 질문은 대처 방법도 필요하고 신고 기관도 필요하다. RAG만 쓰면 신고 정보가 애매해지고, DB만 쓰면 실제 대처 방법이 빈약해진다.

이 부분을 구현하면서 느낀 건, LangGraph는 단순히 노드를 예쁘게 이어 붙이는 도구가 아니라는 점이다. “어떤 질문을 어떤 근거로 처리할지”를 코드로 고정하는 도구에 가깝다.

# 5. RAG와 Text2SQL을 나눠서 쓴 이유

RAG는 설명에 강하다. PDF 문서에서 관련 내용을 찾아와서 “왜 위험한지”, “어떤 설정을 확인해야 하는지”를 풀어줄 수 있다.

Text2SQL은 정확한 조회에 강하다. 예를 들어 KISA 118 상담센터, 경찰청 ECRM, 사고 유형 목록 같은 정보는 DB에서 직접 가져오는 게 맞다.

그래서 이 프로젝트에서는 둘 중 하나만 고르지 않았다.

질문이 보안 원리나 대처 방법이면 RAG.
질문이 목록, 개수, 연락처, 신고 기관이면 DB.
둘 다 필요하면 hybrid.

이렇게 나눴다.

구현 중에 제일 많이 신경 쓴 건 **안전한 SQL 실행**이었다. LLM이 SQL을 직접 만들기 때문에, 아무 쿼리나 실행하면 위험하다. 그래서 SELECT 계열만 허용하고, 결과 개수도 제한하는 방향으로 잡았다.

실제 서비스라면 여기서 더 강하게 막아야 한다. 허용 테이블 목록, LIMIT 강제, 위험 키워드 차단, 실행 전 검증 같은 게 기본으로 들어가야 한다.

이 프로젝트를 하면서 Text2SQL은 “자연어를 SQL로 바꿔서 편하다”에서 끝나면 안 된다는 걸 느꼈다. 편한 만큼 실행 권한이 생기기 때문에, 보안 프로젝트에서는 더 조심해서 다뤄야 한다.

# 6. 일반 사용자용 UI

처음 UI는 기능 확인용에 가까웠다. 개발자가 보기에는 문제가 없지만, 일반 사용자가 쓰기에는 너무 딱딱했다.

그래서 첫 화면부터 다시 잡았다.

![IoT 디바이스 보안 점검 도우미 홈화면](/image/2026-08-27-iot-security-helper/home-screen.png)

처음 들어왔을 때 바로 질문 예시가 보이도록 했다. 사용자가 빈 입력창만 보면 뭘 물어봐야 할지 모를 수 있어서, 웹캠·공유기·스마트 도어락처럼 바로 떠올릴 수 있는 상황을 카드로 넣었다.

답변 화면은 아래처럼 구성했다.

![IoT 디바이스 보안 점검 도우미 화면](/image/2026-08-27-iot-security-helper/iot-security-helper-ui.png)

왼쪽에는 바로 눌러볼 수 있는 해킹 사례를 넣었다.

- Mirai 봇넷
- 스마트 CCTV 해킹
- 스마트 도어락 취약점
- 의료기기 해킹
- 차량 IoT 해킹

메인 화면에서는 “웹캠·홈캠, 스마트 도어락, 공유기, 스마트TV”처럼 익숙한 기기 이름을 먼저 보여줬다.

원래는 `JTAG`, `UART`, `MCU`, `펌웨어 무결성` 같은 말이 앞에 나왔다. 그런데 일반 사용자 입장에서는 그게 먼저 보이면 바로 어렵다.

그래서 답변 흐름도 바꿨다.

```text
상황 판단
→ 지금 바로 할 조치
→ 보안 점검 체크리스트
→ 추가 도움 / 신고
→ 참고 자료
```

예를 들어 웹캠이 혼자 움직인다고 하면, 처음부터 “원격 접근 취약점” 같은 말을 길게 설명하지 않는다.

먼저 전원을 끄거나 인터넷 연결을 잠시 끊으라고 안내한다. 그 다음 관리자 비밀번호, 공유기 비밀번호, 연결된 기기 목록, 원격 접속 기능, 펌웨어 업데이트를 확인하게 한다.

기술적으로 맞는 답변이어도 사용자가 바로 따라 하지 못하면 의미가 약하다고 봤다.

# 7. 만들면서 부딪힌 부분

제일 헷갈렸던 건 라우팅이었다.

처음에는 모든 질문이 일반 답변으로 빠지는 문제가 있었다. 질문 분류 모델이 `iot_consult`, `database`, `hybrid` 같은 값을 정확히 반환해야 하는데, 조금만 다른 문장이 나오면 기본값인 `general`로 떨어졌다.

이 문제를 보면서 “LLM이 알아서 잘 분류하겠지”라고 두면 안 된다는 걸 느꼈다. 분류 결과는 결국 다음 노드를 결정하는 제어 신호다. 제어 신호가 흔들리면 전체 에이전트가 틀어진다.

또 하나는 Qdrant 필터링이었다. 문서에 카테고리 메타데이터를 넣어도, payload index가 없으면 필터 검색이 제대로 안 된다. 단순히 벡터를 넣는 것과 검색 조건까지 안정적으로 쓰는 건 다른 문제였다.

Text2SQL 쪽에서는 SQLAlchemy 2.x 호환 문제도 있었다. 문자열 SQL을 그대로 넘기면 오류가 나서 `sqlalchemy.text()`로 감싸야 했다. 이런 건 발표 자료만 보면 작아 보이는데, 실제 구현할 때는 시간을 꽤 잡아먹는다.

# 8. 구현 결과

최종 구조는 다음과 같다.

- 사용자가 일상어로 IoT 보안 질문을 입력한다.
- 에이전트가 질문을 다시 정리한다.
- 질문 의도를 분류한다.
- PDF 문서 검색, DB 조회, 또는 둘 다 실행한다.
- 결과를 합쳐서 일반 사용자 눈높이로 답변한다.
- 답변이 부족하면 다시 보완한다.

이번 작업에서는 RAG, Text2SQL, LangGraph, Streamlit을 따로 쓰는 것보다 각 기능을 언제 써야 하는지 정하는 게 더 중요했다.

# 9. 회고

이번 프로젝트에서 신경 쓴 부분은 IoT 보안을 일반 사용자 문제로 바꾸는 것이었다.

보안 프로젝트를 만들다 보면 자꾸 기술 키워드를 앞세우게 된다. JTAG, secure boot, 암호화, 접근통제 같은 단어를 쓰면 뭔가 있어 보인다. 그런데 실제 사용자는 “우리 집 홈캠이 이상한데 지금 뭘 해야 하지?”가 먼저다.

그래서 이번에는 기술을 뒤로 숨기고, 사용자의 상황을 앞에 뒀다.

내부는 Qdrant, Supabase, LangGraph 노드가 엮여 있어서 생각보다 복잡하다. 하지만 화면에서는 그 복잡함이 최대한 드러나지 않게 했다.

공부한 내용을 기능으로 만들고, 그 기능을 사용자가 이해할 수 있는 화면으로 정리한 프로젝트였다.
