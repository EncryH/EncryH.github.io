# 1. 프로젝트 배경

최근 다양한 분야에서 AI 기술이 빠르게 적용되며 발전되고 있다. 하나의 기술에 대해 알게 되면 다음날 또 새로운 기술이 등장할 정도로 변화가 빠른 요즘, 나는 이러한 AI 기술을 단순히 사용하는 것에 그치지 않고 직접 이해하고 활용할 수 있는 역량을 갖추고 싶다는 생각을 하게 되었다.

정보보안을 공부하면서 자연스럽게 AI 기술을 접할 기회가 많아졌고, 그 과정에서 LLM, AI Agent와 같은 생성형 AI 기술에 관심도 점점 커지게 되었다. 그러던 중  "인공지능 기반 상명 AI Training"에 참여하게 되었다.

# 2. 교육과정 및 학습 내용 

이번 "인공지능 기반 상명 AI Training"은 생성형 AI의의 기본 개념을 학습한 뒤, RAG와 Text2SQL을 활용해 외부 데이터를 연결하고 이를 하나의 AI 서비스로 구현하는 방식으로 진행되었다.

교육 초반에는 LLM의 기본 구조와 RAG(Retrival-Augmented Generation) 개념을 학습하였다. 단순히 LLM 자체의 지식만을 활용하는 것이 아니라, 필요한 정보를 외부 데이터에서 검색하고 이를 답변 생성에 활용하는 과정을 실습하며 RAG의 전체적인 동작 구조를 이해할 수 있었다.

이후에는 RAG를 조금 더 발전시켜 문서 데이터를 검색하는 방법과 함께, Text2SQL을 활용해 자연어 질문을 SQL로 변환하고 데이터베이스의 정보를 조회하는 방식을 학습하였다.

이 과정에서 문서 기반의 비정형 데이터를 검색하는 RAG와, 데이터베이스의 정형 데이터를 조회하는 Text2SQL이 서로 다른 형태의 데이터를 활용한다는 점이 흥미로웠다.

이후에는 두 방식을 하나의 흐름으로 결합하여 RAG + Text2SQL 기반 데이터 조회 시스템을 구현하였고, 지금까지 배운 내용을 실제 서비스 형태로 적용하기 위한 프로젝트를 진행하게 되었다.

# 3. 프로젝트 주제 선정

팀 프로젝트를 시작하면서 가장 고민한 것은 팀원의 전공을 어떻게 하나의 주제로 연결할 것인가였다. 우리 팀은 전자공학과 2명과 정보보안공학과를 전공하고 있는 나로 구성되어, 전자공학의 하드웨어와 정보보안의 보안 기술을 함께 활용할 수 있는 주제를 생각하게 되었다.

여러 아이디어를 고민하던 중 두 분야의 접점으로 IoT 디바이스 보안으로 주제가 좁혀졌다. IoT 기기는 다양한 하드웨어가 네트워크에 연결되어 동작하기 때문에 디바이스 자체의 정보뿐만 아니라 보안 취약점과 위험 요소를 함께 점검하는 것이 중요하다고 생각했다.

이에 교육에서 학습한 RAG와 Text2SQL을 활용해 IoT 디바이스 정보를 조회하고, 관련 보안 자료를 바탕으로 보안 상태를 점검할 수 있는 "IoT 디바이스 보안 점검 도우미"를 프로젝트 주제로 선정하였다.

# 4. 프로젝트 설계 및 구현

주제 선정 후 IoT 디바이스 정보와 보안 관련 데이터를 하나의 AI 서비스에서 어떻게 활용할 것인지를 중심으로 시스템을 설계하였다.

먼저 데이터의 형태에 따라 역할을 구분하였다. IoT 보안 관련 공식 가이드 PDF를 수집하여 RAG 검색을 위한 문서 데이터로 활용하였다. 주요 핵심 자료로는 "IoT 공통 보안 가이드"와 KISA의 "홈·가전 IoT 보안가이드"를 활용하였으며, 문서를 Chunk 단위로 분할하여 Vector DB에 저장하였다.

또한 신고 기관, 사고 유형, 보안 점검 항목 등 정형화 할 수 있는 IoT 보안 정보를 CSV 형태로 구성한 뒤 Supabase에 적재하고, 사용자의 자연어 질문을 SQL로 변환하는 Text2SQL을 통해 필요한 정보를 조회하도록 구하였다.

이렇게 구성된 RAG와 Text2SQL의 처리 과정을 하나의 흐름으로 연결하기 위해 LangGraph를 활용하였다. 사용자의 질문을 먼저 분석하고 의도를 분류한 뒤, 질문 유형에 따라 RAG 검색, Text2SQL 기반 DB 조회 또는 두 기능을 함께 실행 하도록 분기하였다. 이후 검색된 결과를 바탕으로 최종 답변을 생성하고 검증하는 워크플로우를 구성하였다.

마지막으로 사용자가 서비스를 쉽게 사용할 수 있도록 Streamlit 기반의 UI를 구현하였다. 사용자가 일상적인 표현으로 IoT 보안 관련 질문을 입력하면 내부의 LangGraph 워크플로우가 필요한 데이터를 검색 및 조회하고, 최종적으로 보안 점검 방법과 대응 방안, 필요한 경우 신고 기관 정보까지 하나의 답변으로 제공하도록 구현하였다.

# 5. LangGraph 구조

앞서 구성한 서비스의 LangGrap의 구조이다.

![IoT 보안 점검 도우미 LangGraph 워크플로우](/image/2026-08-27-iot-security-helper/langgraph-workflow.png)

핵심은 질문을 바로 답변 생성으로 보내지 않는 것이다. 먼저 질문을 정리하고, 의도를 분류한 뒤에 경로를 나눈다.

```text
질문 분석
→ 의도 분류
→ RAG 검색 / DB 조회 / RAG+DB 통합
→ 답변 생성
→ 답변 검증
```

의도는 네 가지로 나눴다.

| 의도 | 처리 방식 |
|------|-----------|
| general | 서비스 소개나 일반 대화 |
| iot_consult | PDF 기반 보안 가이드 검색 |
| database | 신고 기관, 사고 유형, 보안 항목 DB 조회 |
| hybrid | 문서 검색과 DB 조회를 함께 실행 |

예를 들어 “웹캠이 해킹된 것 같은데 어떻게 점검하고 어디에 신고해?”는 `hybrid`로 보내야 한다.

이 질문은 대처 방법도 필요하고 신고 기관도 필요하다. RAG만 쓰면 신고 정보가 애매해지고, DB만 쓰면 실제 대처 방법이 빈약해진다.

이 부분을 구현하면서 느낀 건, LangGraph는 단순히 노드를 예쁘게 이어 붙이는 도구가 아니라는 점이다. “어떤 질문을 어떤 근거로 처리할지”를 코드로 고정하는 도구에 가깝다.

# 6. 일반 사용자용 UI 설계

처음 UI는 기능 확인용에 가까웠다. 개발자가 보기에는 문제가 없지만, 일반 사용자가 쓰기에는 너무 딱딱했다.

그래서 첫 화면부터 다시 잡았다.

![IoT 디바이스 보안 점검 도우미 홈화면](/image/2026-08-27-iot-security-helper/home-screen.png)

처음 들어왔을 때 바로 질문 예시가 보이도록 했다. 사용자가 빈 입력창만 보면 뭘 물어봐야 할지 모를 수 있어서, 웹캠·공유기·스마트 도어락처럼 바로 떠올릴 수 있는 상황을 카드로 넣었다.

답변 화면은 아래처럼 구성했다.

![IoT 디바이스 보안 점검 도우미 화면](/image/2026-08-27-iot-security-helper/iot-security-helper-ui.png)

왼쪽에는 바로 눌러볼 수 있는 해킹 사례를 넣었다.

- Mirai 봇넷
- 스마트 CCTV 해킹
- 스마트 도어락 취약점
- 의료기기 해킹
- 차량 IoT 해킹

메인 화면에서는 “웹캠·홈캠, 스마트 도어락, 공유기, 스마트TV”처럼 익숙한 기기 이름을 먼저 보여줬다.

원래는 `JTAG`, `UART`, `MCU`, `펌웨어 무결성` 같은 말이 앞에 나왔다. 그런데 일반 사용자 입장에서는 그게 먼저 보이면 바로 어렵다.

그래서 답변 흐름도 바꿨다.

```text
상황 판단
→ 지금 바로 할 조치
→ 보안 점검 체크리스트
→ 추가 도움 / 신고
→ 참고 자료
```

예를 들어 웹캠이 혼자 움직인다고 하면, 처음부터 “원격 접근 취약점” 같은 말을 길게 설명하지 않는다.

먼저 전원을 끄거나 인터넷 연결을 잠시 끊으라고 안내한다. 그 다음 관리자 비밀번호, 공유기 비밀번호, 연결된 기기 목록, 원격 접속 기능, 펌웨어 업데이트를 확인하게 한다.

기술적으로 맞는 답변이어도 사용자가 바로 따라 하지 못하면 의미가 약하다고 봤다.

# 7. 만들면서 부딪힌 부분

제일 헷갈렸던 건 라우팅이었다.

처음에는 모든 질문이 일반 답변으로 빠지는 문제가 있었다. 질문 분류 모델이 `iot_consult`, `database`, `hybrid` 같은 값을 정확히 반환해야 하는데, 조금만 다른 문장이 나오면 기본값인 `general`로 떨어졌다.

이 문제를 보면서 “LLM이 알아서 잘 분류하겠지”라고 두면 안 된다는 걸 느꼈다. 분류 결과는 결국 다음 노드를 결정하는 제어 신호다. 제어 신호가 흔들리면 전체 에이전트가 틀어진다.

또 하나는 Qdrant 필터링이었다. 문서에 카테고리 메타데이터를 넣어도, payload index가 없으면 필터 검색이 제대로 안 된다. 단순히 벡터를 넣는 것과 검색 조건까지 안정적으로 쓰는 건 다른 문제였다.

Text2SQL 쪽에서는 SQLAlchemy 2.x 호환 문제도 있었다. 문자열 SQL을 그대로 넘기면 오류가 나서 `sqlalchemy.text()`로 감싸야 했다. 이런 건 발표 자료만 보면 작아 보이는데, 실제 구현할 때는 시간을 꽤 잡아먹는다.

# 8. 구현 결과

최종 구조는 다음과 같다.

- 사용자가 일상어로 IoT 보안 질문을 입력한다.
- 에이전트가 질문을 다시 정리한다.
- 질문 의도를 분류한다.
- PDF 문서 검색, DB 조회, 또는 둘 다 실행한다.
- 결과를 합쳐서 일반 사용자 눈높이로 답변한다.
- 답변이 부족하면 다시 보완한다.

이번 작업에서는 RAG, Text2SQL, LangGraph, Streamlit을 따로 쓰는 것보다 각 기능을 언제 써야 하는지 정하는 게 더 중요했다.

# 9. 회고

이번 프로젝트에서 신경 쓴 부분은 IoT 보안을 일반 사용자 문제로 바꾸는 것이었다.

보안 프로젝트를 만들다 보면 자꾸 기술 키워드를 앞세우게 된다. JTAG, secure boot, 암호화, 접근통제 같은 단어를 쓰면 뭔가 있어 보인다. 그런데 실제 사용자는 “우리 집 홈캠이 이상한데 지금 뭘 해야 하지?”가 먼저다.

그래서 이번에는 기술을 뒤로 숨기고, 사용자의 상황을 앞에 뒀다.

내부는 Qdrant, Supabase, LangGraph 노드가 엮여 있어서 생각보다 복잡하다. 하지만 화면에서는 그 복잡함이 최대한 드러나지 않게 했다.

공부한 내용을 기능으로 만들고, 그 기능을 사용자가 이해할 수 있는 화면으로 정리한 프로젝트였다.
