# 1. 프로젝트 배경

"인공지능 기반 상명 AI Training"에서 진행한 두 번째 팀 프로젝트다.

첫 번째 프로젝트에서는 RAG와 Text2SQL을 LangGraph로 묶어 [IoT 디바이스 보안 점검 도우미](/activity/iot-security-helper-agent/)를 만들었다. 그때는 문서와 DB에서 필요한 정보를 찾아 답변에 넣는 게 중심이었고, 교육 후반부에는 도구를 직접 골라 쓰는 AI Agent를 배웠다.

같은 팀원들과 이번에는 여러 LLM의 답변을 실제로 비교하고 평가하는 에이전트를 만들었다.

# 2. 교육과정 및 학습 내용

후반부 교육은 Agent의 기본 패턴을 익힌 뒤, 거기에 안전장치와 작업 지침을 하나씩 얹는 순서로 진행되었다.

7일차에는 LangChain v1의 `create_agent`로 기본 Agent를 만들고, Tavily 웹 검색 Agent와 도메인 특화 Agent를 실습하였다. Agent가 쓸 Tool을 정의하고 LangGraph Studio로 실행 흐름을 확인하는 방법도 이때 배웠다.

8일차에는 Middleware를 배웠다. Agent 실행 전, 모델 호출 전후, Tool 호출 시점에 코드를 끼워 넣어 입력을 검사하거나 응답을 손보는 방식이다. 팀별로 가드레일이나 폴백 같은 동작 제어 로직을 직접 구현해 보았다.

9일차에는 `SKILL.md` 기반 Skill을 다뤘다. 긴 작업 지침을 시스템 프롬프트에 다 넣지 않고, 필요할 때만 불러와서 Agent가 따르게 하는 구조다. 10일차에는 팀별로 Agent를 다듬고 최종 발표를 했다.

돌아보면 첫 번째 프로젝트는 데이터를 어떻게 찾아올지에 대한 고민이었고, 두 번째 프로젝트는 Agent가 할 수 있는 일과 하면 안 되는 일을 코드로 정하는 작업이었다.

# 3. 프로젝트 주제 선정

주제를 고민하다 보니 쓸 수 있는 LLM이 너무 많다는 게 먼저 눈에 들어왔다. Groq API만 해도 Meta Llama, OpenAI gpt-oss, Alibaba Qwen, MiniMax 등 여러 계열의 오픈 모델을 제공한다. 아래는 Groq 공식 문서의 모델 목록 일부인데, 모델마다 속도, 가격, 요청 한도, 컨텍스트 길이가 제각각이다.

![Groq 공식 문서의 Production Models 목록](/image/2026-09-11-open-llm-battle-agent/groq-models-production.png)

모델을 고를 때는 보통 벤치마크 점수나 인지도를 보게 된다. 하지만 내 질문에 어떤 모델이 더 잘 답하는지는 직접 물어보기 전까지 알기 어렵다.

그래서 같은 질문을 여러 모델에 동시에 보내고, 실제 답변의 품질과 응답 속도를 비교해 보고서로 남기는 에이전트를 만들기로 했다. 이름값보다 같은 조건에서 나온 실제 답변으로 비교해 보자는 취지였고, 이름은 "Open LLM Battle Agent"로 정했다.

정보보안을 전공하는 입장에서 따로 챙기고 싶은 것도 있었다. 평가가 특정 모델 쪽으로 기울지 않게 만드는 것, 그리고 파일을 읽고 쓰는 Agent가 위험한 요청이나 작업을 하지 못하게 막는 것이다.

# 4. 프로젝트 설계 및 구현

전체 흐름은 다음과 같다.

```text
사용자 질문
→ 위험 입력 검사, 평가 Skill 로드
→ Groq 모델 조회·선택 (2~4개)
→ 동일한 질문과 조건으로 실행
→ 답변·응답 시간 수집
→ 익명 직접 평가 + 위치 교환 Pairwise 비교
→ 최종 순위와 Markdown 보고서 저장
```

구성 요소는 역할별로 네 부분으로 나눴다.

| 구분 | 구현 | 역할 |
|------|------|------|
| Agent | `agent.py` | `create_agent`로 모델, Tool, Middleware를 연결 |
| Tool | `tools.py` | 모델 조회·실행, 보고서 저장, 파일 읽기·쓰기, Skill 로드 |
| Middleware | `middleware.py` | 입력 검사, 개인정보 마스킹, 파일 작업 보호 |
| Skill | `SKILL.md` | 답변 평가 절차와 채점 기준 |

핵심 Tool은 `save_open_llm_report`다. Groq에서 지금 사용할 수 있는 모델 목록을 조회하고, 지정된 모델이나 무작위로 고른 모델에 같은 질문을 보낸 다음, 답변 원문과 응답 시간을 담아 초기 보고서를 저장한다.

모델은 `random:2~4` 또는 `models:모델명` 방식으로 고를 수 있다. 무작위로 고를 때는 같은 계열끼리만 붙지 않도록 계열이 다른 모델을 먼저 뽑게 했고, 한 번에 비교하는 모델은 최대 4개로 제한했다.

Agent는 `create_agent`에 모델, Tool, Middleware를 넘겨 만들었다. Middleware는 순서대로 실행되기 때문에 입력 검사가 가장 먼저 돌도록 배치했다.

개발은 교육 일정에 맞춰 조금씩 확장했다. 7일차에 Tool만 있는 기본 Agent를 만들고, 8일차에 Middleware, 9일차에 평가 Skill을 붙였다.

# 5. Agent 구조

LangGraph Studio에서 확인한 실행 구조다.

![Open LLM Battle Agent LangGraph Studio 그래프](/image/2026-09-11-open-llm-battle-agent/langgraph-studio.png)

첫 번째 프로젝트에서는 노드 11개와 분기를 직접 그렸다. 이번에는 `create_agent`가 `model`과 `tools`를 오가는 기본 루프를 만들어 주고, 그 사이사이에 Middleware가 들어간다.

```text
__start__
→ request_safety_middleware (before_agent)
→ workspace_index_middleware (before_agent)
→ model ⇄ tools
→ response_pii_masking_middleware (after_model)
→ __end__
```

눈여겨볼 부분은 `request_safety_middleware`에서 `__end__`로 바로 빠지는 선이다. 위험한 입력이 들어오면 모델을 한 번도 부르지 않고 거기서 실행이 끝난다.

그래프를 직접 그릴 필요가 없다 보니, 설계 시간 대부분은 어느 시점에 무엇을 검사할지 정하는 데 들어갔다.

# 6. Middleware 안전 설계

보안과 가장 직접 맞닿아 있는 부분이다. Middleware는 동작 시점에 따라 다섯 개를 두었다.

| Middleware | 시점 | 역할 |
|------|------|------|
| `request_safety_middleware` | Agent 실행 전 | 빈 입력, 프롬프트 인젝션 패턴, 개인정보 입력 차단 |
| `workspace_index_middleware` | Agent 실행 전 | Workspace 문서 목록을 컨텍스트로 제공 |
| `SkillMiddleware` | 모델 호출 시 | 사용 가능한 Skill 목록을 시스템 프롬프트에 추가 |
| `response_pii_masking_middleware` | 모델 응답 후 | 응답의 이메일, 전화번호 등 개인정보 형식 마스킹 |
| `auto_backup_middleware` | Tool 호출 시 | 파일 수정 전 자동 백업, 민감 경로·삭제 요청 차단 |

입력 검사는 모델을 부르기 전에 끝낸다. "시스템 프롬프트", "ignore previous", "관리자 모드" 같은 인젝션 패턴이나 주민등록번호, 전화번호, 이메일, 카드번호 형식이 보이면 `jump_to: "end"`로 곧바로 실행을 종료한다.

![request_safety_middleware - 인젝션 패턴과 개인정보 입력 차단](/image/2026-09-11-open-llm-battle-agent/code-request-safety.png)

파일 작업도 막아 두었다. 이 Agent는 보고서를 저장하려고 파일 쓰기 권한을 갖고 있어서, 잘못 동작하면 중요한 파일을 덮어쓸 수도 있다. 그래서 Tool이 실행되기 직전에 경로를 확인해 `.env`, `.git`, 가상환경 같은 민감 경로는 건드리지 못하게 하고, 파일 삭제 요청은 아예 막았다. 파일을 수정할 때는 원본을 `backup` 폴더에 먼저 복사해 둔다.

Prompt Injection, Data Leakage, Tool Abuse를 개념으로만 알고 있었는데, 이번에 처음으로 Agent 코드 안에서 직접 막아 봤다.

# 7. Advanced Evaluation Skill

평가 절차는 `advanced-evaluation` Skill로 따로 뺐다. 평가 규칙이 길어서 시스템 프롬프트에 늘 넣어 두기엔 부담스러웠다. `SkillMiddleware`는 Skill 이름과 설명만 알려 주고, 모델 비교 요청이 왔을 때만 `load_skill`로 전체 지침을 불러오게 했다.

Skill에는 먼저 평가 원칙을 적어 두었다.

- 모델의 평판이 아니라 실제로 생성된 답변만 평가한다.
- 모든 모델에 같은 질문, 같은 언어 조건, 같은 최대 출력 길이를 적용한다.
- 답변 원문은 고치지 않고, 평가는 별도 섹션에 쓴다.
- 평가하는 동안에는 모델 이름을 가리고 응답 A, B, C, D로만 부른다.
- 응답 속도와 답변 길이는 품질 점수에 넣지 않는다.
- 차이가 뚜렷하지 않으면 억지로 승자를 정하지 않고 동률로 둔다.

채점 기준은 질문 유형마다 달라진다. 질문을 사실 및 개념 설명, 기술 및 코드, 분석 및 추천, 요약 및 변환, 창작 및 아이디어, 절차 및 문제 해결 중 하나로 분류한 뒤, 유형에 맞는 기준을 최대 5개까지 가중치 합 100으로 정한다.

직접 채점과 별개로 두 답변을 맞붙이는 Pairwise 비교도 한다. 이때 같은 조합을 답변 순서만 바꿔 한 번 더 평가한다. LLM이 평가를 맡으면 먼저 나온 답변을 더 좋게 보는 위치 편향이 생길 수 있어서, 두 결과가 엇갈리면 동률로 처리했다.

![advanced-evaluation SKILL.md - 직접 채점, 위치를 바꾼 Pairwise 비교, 최종 순위 계산 단계](/image/2026-09-11-open-llm-battle-agent/skill-pairwise.png)

# 8. 만들면서 부딪힌 부분

처음 부딪힌 건 모델 목록이었다. Groq 모델 목록에는 채팅 모델만 있는 게 아니었다. 아래 Preview Models 목록만 봐도 음성 합성 모델(Orpheus)과 입력 검사 모델(Prompt Guard, Safeguard)이 채팅 모델과 같은 표에 들어 있다.

![Groq 공식 문서의 Preview Models 목록 - 음성 합성·입력 검사 모델이 함께 있다](/image/2026-09-11-open-llm-battle-agent/groq-models-preview.png)

API로 목록을 조회하면 이런 모델에 음성 인식용 Whisper까지 같이 나온다. 여기에 질문을 보내면 비교가 성립하지 않아서, 이름으로 걸러내는 목록을 따로 만들었다. `groq/compound`는 내부에서 도구까지 실행하는 시스템이라 일반 모델과 나란히 놓고 비교하기 어려워 무작위 비교에서 뺐다.

다음은 답변 언어였다. 모델에 따라 `<think>` 태그로 내부 추론이 그대로 섞여 나오거나, 한국어로 물어도 다른 언어로 답할 수 있었다. 그래서 품질을 보기 전에 질문한 언어로 답했는지부터 확인해야 했다. 추론 태그는 지우고, 남은 답변에서 한글 비율이 너무 낮으면 정상 답변으로 치지 않도록 했다.

마지막은 실패하는 모델이었다. 작은 모델은 출력 토큰 한도에 걸려 답이 중간에 끊기거나, 같은 말을 되풀이하다 질문과 상관없는 얘기로 흘러가기도 했다. 분당 토큰 한도(TPM)를 넘겨 아예 응답을 못 받는 경우도 있었다.

여기서 중요한 건 실패한 모델을 슬쩍 다른 모델로 바꾸지 않는 것이었다. Agent가 알아서 모델을 바꾸거나 끊긴 답변을 다듬어 버리면 비교 결과를 믿을 수 없다. 그래서 실패한 모델은 원인과 함께 보고서에 남기고 평가에서만 빼도록 했다. 모델 교체, 원문 수정, 비교 도구 중복 호출은 시스템 프롬프트와 Skill 양쪽에 금지 규칙으로 적었다.

# 9. 구현 결과

쇼핑몰 고객지원 상황을 가정한 질문으로 모델 3개를 비교한 보고서를 예로 들면 이렇다. 보고서 앞부분에는 모델별 상태, 응답 시간, 답변 길이, 종료 사유가 정리되는데, 여기서는 `allam-2-7b`가 출력 토큰 한도에 걸려 실패로 기록됐고 나머지 두 모델만 평가를 받았다.

평가가 끝나면 보고서 뒤쪽에 Pairwise 결과와 최종 순위가 붙는다. 이 질문에서는 `openai/gpt-oss-120b`가 직접 평가 98.0점을 받았고, 순서를 바꾼 Pairwise 비교에서도 두 번 모두 이겨 1위가 됐다. 판정 신뢰도는 '높음'이었다. 최종 점수 98.6점은 직접 평가 점수 70%와 Pairwise 점수 30%를 합친 값이다.

![비교 보고서 - Pairwise 비교와 최종 순위](/image/2026-09-11-open-llm-battle-agent/report-ranking.png)

응답 속도는 오히려 `qwen/qwen3.6-27b`가 0.848초로 더 빨랐다. 품질 1위와 속도 1위가 다를 수 있으니, 두 지표를 보고서에서 따로 본 게 의미가 있었다.

발표 때는 보안·기술 질문 3개(프롬프트 인젝션 설명, RAG에서 인젝션이 위험한 이유, RAG 문서 오염 방어)와 일반 질문 2개(스마트폰 배터리 절약법, 약속에 못 갈 때 보낼 메시지)로 테스트했다. 질문 유형에 따라 채점 기준이 바뀌고, 질문마다 보고서가 따로 저장된다.

# 10. 회고

이번 프로젝트를 하면서 AI 엔지니어링이 좋은 모델을 고르는 일이라기보다, 모델을 둘러싼 시스템을 설계하는 일에 더 가깝다는 생각이 들었다.

모델을 비교하는 에이전트였는데도 정작 중요했던 건 호출 코드가 아니라 어떤 답을 좋은 답으로 볼지 정하는 부분이었고, 루브릭과 가중치, 동률 기준을 글로 적어 두지 않으면 나중에 결과를 설명하기도 재현하기도 어려웠다. 평가를 맡은 LLM 역시 편향에서 자유롭지 않기 때문에, 익명화나 순서 바꾸기 같은 장치까지 평가 설계 안에 넣어야 했다.

LLM에게 맡길 일과 코드로 고정할 일을 나누는 것도 이번에 배운 부분이다. 답변 평가와 보고서 작성은 LLM에게 맡기되, 위험한 입력 차단이나 민감 경로 보호, 파일 백업, 비채팅 모델 필터링, 한국어 답변 판정처럼 결과가 항상 같아야 하는 일은 코드로 처리했다. 프롬프트에 적은 규칙은 어디까지나 모델이 지켜 주길 바라는 것에 가깝지만 코드로 짠 규칙은 매번 그대로 동작하니까, 안전과 바로 연결되는 장치일수록 코드 쪽에 두는 게 맞다고 느꼈다.

컨텍스트 역시 설계할 대상이었는데, 평가 지침을 시스템 프롬프트에 늘 넣어 두는 대신 Skill 목록만 알려 주고 필요할 때 불러오게 하니 토큰을 아끼면서도 그때그때 필요한 지침만 모델에 넘길 수 있었다.

외부 모델 API가 언제든 실패할 수 있다는 것도 직접 겪었다. 실제로 답이 중간에 끊기거나 요청 한도에 걸리는 일이 있었는데, 이런 실패를 예외로 치워 버리지 않고 흐름 안에서 처리하려고 실패한 모델은 따로 떼어 두고 원인을 보고서에 남기도록 했다. 덕분에 모델별 원문과 응답 시간, 판정 근거가 담긴 보고서는 결과물이면서 동시에 나중에 다시 들여다볼 수 있는 실행 기록이 되었다.

아쉬운 점도 남는다. 인젝션 탐지는 키워드 기반이라 표현만 바꿔도 쉽게 우회되고, 개인정보 마스킹 역시 정해진 형식만 잡아낸다. 또 모델마다 한 번씩만 돌려 비교했기 때문에 같은 질문에서 답변이 얼마나 달라지는지는 확인하지 못했고, 평가자 모델도 하나뿐이라 그 모델의 취향이 결과에 섞였을 가능성도 있다.

그래서 다음에는 키워드 검사 앞에 Prompt Guard 같은 분류 모델을 붙여 탐지를 한 겹 더 두고, 같은 질문을 여러 번 돌려 편차까지 함께 보면서, 다른 평가자 모델로 교차 검증하는 방향으로 발전시켜 보고 싶다. 이번에 만든 평가 구조는 앞으로 RAG 시스템의 보안 평가 같은 작업에도 활용해 볼 생각이다.
